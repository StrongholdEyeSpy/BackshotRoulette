# План: помощник для Buckshot Roulette

Помощник считает лучший ход по ситуации за столом и показывает его поверх игры. Работает в одиночке и в мультиплеере на 2–4 игрока. Приложение пишется с нуля: код старого бота не переиспользуется.

## Рамки

Что делаем:

- мод для Steam-версии на ПК (Windows и Linux), который снимает состояние стола и выводит подсказку;
- движок, который по этому состоянию оценивает ходы: шанс на победу для каждого хода, вероятность боевого патрона, лучшую линию;
- обученную оценку позиции (маленькая нейросеть + self-play), которая подключается к поиску.

Допущения (поправить, если не так):

- в одиночке Dealer считается рациональным противником, как любой другой игрок;
- помощник только советует и не нажимает кнопки за игрока;
- движок получает только то, что видит игрок. Реальную последовательность патронов мод не читает.

Вне рамок: полный AlphaZero или MCCFR, модель поведения живых игроков по логам, разбор партий после игры, перенос скрипта Dealer, конфиги правил под разные версии игры, версия для Xbox/Game Pass.

## Стек

| Часть | Язык | Почему |
|---|---|---|
| Движок, симулятор, сервер | Rust | Поиск и self-play упираются в скорость; один бинарник без рантайма; нормальная многопоточность |
| Обучение | Python + PyTorch | Удобно экспериментировать; симулятор вызывается из Rust через PyO3 |
| Мод | GDScript | Игра сделана на Godot 4.1.1, мод строится на godot-mod-loader через script extensions |
| Ручной ввод | HTML + JS без фреймворка | Его раздаёт тот же сервер, работает в любом браузере |

Нейросеть в рантайме считает сам Rust. Для MLP на несколько тысяч параметров прямой проход — это пара умножений матриц, ONNX-рантайм для этого не нужен. Если сеть сильно вырастет, перейдём на `tract`.

## Архитектура

```
 Игра (Godot) + мод                           Движок (Rust, отдельный процесс)
 ┌───────────────────────┐   WebSocket,        ┌───────────────────────────────┐
 │ трекер состояния ─────┼── JSON-снимок ─────▶│ сервер ─▶ поиск ─▶ оценка     │
 │ оверлей ◀─────────────┼── анализ ───────────┤   ▲        (эвристика / MLP)  │
 └───────────────────────┘   127.0.0.1         │   └── ручной UI (браузер)     │
                                               └───────────────────────────────┘
                      Обучение (Python) ◀── PyO3 ── симулятор (Rust)
```

- Мод на каждое изменение стола отправляет полный снимок состояния. Диффов нет: снимки проще отлаживать, и потерянное сообщение ничего не ломает.
- Движок между запросами помнит только кэш позиций. Новый снимок отменяет текущий расчёт.
- Обновление игры может сломать только мод. Движок и ручной UI продолжают работать.

## Модель состояния

Состояние строится с точки зрения одного игрока («я»).

- **Игроки** (до 4): HP, максимум HP, предметы как вектор счётчиков (не больше 8), действует ли Jammer или Handcuffs, жив ли.
- **Очередь**: чей ход и направление (±1, Remote его разворачивает).
- **Ружьё**: распилено ли; сколько осталось боевых и холостых *из исходной зарядки*; флаг «текущий патрон перевёрнут Inverter»; позиции, которые знаю я, и их значения; позиции, которые знает каждый соперник (только сам факт, значения нам неизвестны).
- **Незавершённое действие**: например, выбор цели после Adrenaline.

Ключевые решения:

- **Патроны раскрываются лениво.** Значение патрона разыгрывается только в тот момент, когда оно становится известно: выстрел, Beer, мои Magnifying Glass и Burner Phone. Так мои решения в дереве никогда не опираются на то, чего я не знаю.
- **Вероятность учитывает известные позиции.** P(текущий боевой) = (осталось боевых − известных мне боевых дальше по магазину) / (число неизвестных позиций).
- **Inverter не ломает счёт.** Храним состав исходной зарядки и флаг переворота. Когда перевёрнутый патрон раскрывается, разыгрываем исходное значение и показываем обратное.
- **Знание соперника.** Если соперник знает текущий патрон (лупа или телефон на эту позицию), узел случайности ставится перед его решением: он ходит, зная патрон.
- **Adrenaline — составной ход.** «Adrenaline → забрать X у игрока P → применить» считается одним ходом. Окно выбора в игре короткое, поэтому цель кражи считается заранее.

Известное упрощение: соперники в дереве действуют так, будто знают то, что я узнал телефоном. Ошибка небольшая, а исправление дорогое. Это фиксируется в `docs/rules.md`.

## Поиск

**1v1.** Expectiminimax до конца текущей зарядки, значение узла — шанс на победу, таблица транспозиций по компактному ключу состояния. В пределах зарядки расчёт точный. На перезарядке ставится оценка позиции: сначала эвристика, потом нейросеть.

**3–4 игрока.**

- max^n по умолчанию: каждый максимизирует свой шанс победить, значение узла — вектор шансов всех игроков.
- paranoid переключателем: все против меня, задача сводится к 1v1.
- Итеративное углубление по числу выстрелов с бюджетом времени. Если до конца зарядки досчитать не успели, в листе стоит оценка позиции.

**Общее.**

- Отсекаются только ходы, про которые доказано, что они не лучше других (например, лупа при уже известном патроне). Для каждого правила отсечения есть тест: с ним и без него результат одинаковый.
- Бюджет: обычно ответ до 200 мс, максимум 1 с. Это цели, уточним после замеров.
- В ответе: ходы по рейтингу с шансом на победу, вероятность боевого патрона, лучшая линия, глубина и время расчёта.

**Базовая эвристика** (до нейросети): точный расчёт подыгры без предметов через перезарядки плюс поправки за предметы. В подыгре без предметов состояние — только HP и патроны, оно маленькое и решается динамическим программированием. Поправки за предметы сначала ручные, на этапе 7 их подбирает регрессия.

## Обучение оценки

**7a — регрессия.**

- Self-play в Rust, из партий собираются пары «признаки позиции → кто выиграл».
- Линейная модель или градиентный бустинг подбирает поправки за предметы.
- Это базовая линия, с которой сравнивается сеть, и запасной вариант, если сеть не выиграет.

**7b — MLP + self-play.**

- Вход: около 100 признаков. По каждому игроку — HP, предметы, Jammer; по ружью — счётчики, распил, переворот, известные позиции; плюс направление очереди. Места поворачиваются так, чтобы ходящий всегда был первым.
- Сеть: 2 скрытых слоя по 64, на выходе шансы на победу по местам (softmax по живым игрокам).
- Цикл: Rust гоняет партии поиском с текущими весами → Python учит сеть на целях TD(λ) (смесь исхода партии и оценки поиска) → веса экспортируются в Rust → новая версия играет против старой.
- Разнообразие партий даёт сама случайность игры, плюс немного случайных ходов в начале каждой партии.

**Проверка.**

- Новая версия принимается, только если обыгрывает старую с p < 0.05. Сравнение идёт на парных сидах (одинаковые раздачи для обеих версий), порядка 20 тыс. партий на сравнение.
- Точная ошибка сети меряется там, где известен ответ: подыгра без предметов (ответ даёт DP) и позиции, где раунд гарантированно решается в текущей зарядке.
- На остальных позициях проверяется согласованность: оценка сети в середине зарядки против «точный поиск до перезарядки + сеть на перезарядке».

**Критерий остановки.** Если после N итераций сеть при равном времени не обыгрывает эвристику с p < 0.05, основной остаётся эвристика, а сеть — опцией.

## Мод

- **Сборка.** Своя копия игры → GDRE Tools восстанавливает проект → godot-mod-loader со script extensions → экспорт редактором GodotSteam 4.1.1 → бинарный патч против оригинального exe. Распространяется только патч, без файлов игры.
- **Трекер.** Собирает состояние из событий игры: зарядка с объявленными счётчиками, выстрел и его результат, использование предмета, перезарядка, смерть. Каждый кадр внутренности игры не читаются. Какие скрипты расширять, станет ясно на этапе 0. Весь трекер живёт в одном файле, чтобы после патча игры правка была в одном месте.
- **Только видимое.** Сведения о патронах трекер берёт из объявленных счётчиков, раскрытых выстрелов и моих лупы и телефона. Массив патронов игры он не читает. Это проверяется на ревью и простым тестом, который ищет обращения к этому массиву в коде мода.
- **Проверки целостности.** HP в пределах, счётчики неотрицательные, сумма патронов сходится. При рассинхроне оверлей пишет «рассинхрон» и перестаёт советовать.
- **Клиент.** WebSocketPeer с переподключением, движок запускается автоматически через `OS.create_process`.
- **Оверлей.** CanvasLayer поверх игры, включается горячей клавишей. Показывает ходы с шансами, P(боевой) и лучшую линию.
- **Логи.** Каждая партия пишется в JSONL. Логи нужны для отладки трекера и служат регрессионными тестами движка.

## Протокол

JSON по WebSocket на 127.0.0.1. Схема лежит в `protocol/`, версия протокола есть в каждом сообщении.

- `hello` — версии протокола и мода.
- `state` — полный снимок с id. Новый снимок отменяет расчёт предыдущего.
- `analysis` — ответ на снимок: ходы, шансы, линия, служебная статистика. Может приходить несколько раз с растущей глубиной.
- `error` — снимок некорректен, с причиной.

## Тесты

- **Эталонные сценарии**: «состояние + ходы → ожидаемое состояние» в JSON, `tests/fixtures/`. Общие для движка и для проверки трекера.
- **Property-тесты** (proptest): сумма вероятностей исходов равна 1; HP в пределах [0, max]; предметов не больше 8; партия всегда заканчивается.
- **Монте-Карло**: частоты исходов в симуляторе совпадают с распределениями из правил.
- **Поиск**: отсечения не меняют результат; на позициях с известным ответом — точное совпадение.
- **Мод**: логи партий прогоняются через движок без ошибок и рассинхронов.
- **CI** на GitHub Actions: `cargo test`, `clippy`, `fmt`, тесты Python, проверка примеров протокола по JSON Schema.

## Открытые вопросы для этапа 0

Ответы берём из кода игры, а не из вики: источники сейчас расходятся или молчат.

1. Шанс Expired Medicine: 40% (Prima Games) или 50% (гайд в Steam).
2. Пул предметов по режимам: есть ли в мультиплеере Handcuffs и Expired Medicine.
3. Диапазон HP по режимам (для мультиплеера встречается 2–6).
4. Сколько предметов выдаётся при перезарядке, какой лимит инвентаря, как выбираются типы.
5. Как выбирается число боевых и холостых при зарядке.
6. Кто ходит первым после перезарядки.
7. Jammer: сбрасывается ли при перезарядке, что будет, если цель умрёт, можно ли заглушить уже заглушенного.
8. Remote: доступен ли, когда в живых двое.
9. Burner Phone: какие позиции он может показать и что происходит при малом числе патронов (встречается «не меньше 3»).
10. Adrenaline: что нельзя украсть (сам Adrenaline; Hand Saw, если ружьё уже распилено?), можно ли красть у выбывших.
11. Inverter: видят ли другие игроки сам факт переворота.
12. Условие победы в мультиплеере: один раунд или несколько, переносится ли что-то между раундами.
13. Передача хода после холостого выстрела в соперника и после боевого в себя, в том числе в мультиплеере.
14. Что видит клиент в мультиплеере (host-authoritative): приходят ли ему все события, которые нужны трекеру.

## Риски

| Риск | Что делаем |
|---|---|
| Патч игры ломает хуки | трекер в одном месте, проверка рассинхрона, ручной UI как запасной путь |
